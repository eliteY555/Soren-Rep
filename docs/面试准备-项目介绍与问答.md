# 易诊通 (YZT-Medicine) — 面试准备文档

---

## 一、项目定位 & 业务场景

### 一句话定位

> **AI 驱动的智能在线问诊系统** —— 将大模型（LLM）嵌入医疗问诊全流程，从"患者描述病情"到"医生给出诊断"形成完整业务闭环，而非简单的 AI 聊天套壳。

### 适用场景

| 场景 | 说明 |
|------|------|
| **互联网医疗平台** | 类似好大夫在线 / 微医的 AI 预问诊模块，患者挂号前由 AI 采集病情 |
| **医院预问诊系统** | 门诊挂号前的智能分诊——AI 对话收集症状 → 推荐科室 → 生成预问诊报告给医生 |
| **远程医疗 / 互联网医院** | 在线复诊、慢病随访，AI 辅助医生快速了解患者病史变化 |
| **体检报告解读** | 用户上传体检数据 → AI 解读异常指标 → 建议就医方向 |

### 解决的核心痛点

传统在线问诊有两个低效环节：
1. **患者端**：非医学背景，描述病情口语化、碎片化，医生需要反复追问基础信息
2. **医生端**：面对大量常见病问诊，大量时间花在"问基本情况"而非"专业判断"

本系统的思路：**在医患之间加一层 AI 预问诊** —— AI 先把患者的口语描述转成结构化病历，医生拿到的是"半成品"病历而非"原始对话"，直接进入诊断决策。

## 二、核心价值：为什么不是"套壳 AI 聊天"？

> 这是面试官最可能追问的灵魂问题："你这和直接打开通义千问/ChatGPT 问病情有什么区别？"

### 对比表

| 维度 | 直接问通用 AI | 易诊通 |
|------|-------------|--------|
| **交互模式** | 单次问答，无持久化上下文 | 多轮对话记忆持久化到 MongoDB，跨会话保留病史 |
| **业务集成** | 无法操作业务系统 | **Function Calling**：AI 在对话中自动调用后端接口，将口语描述转成结构化病历写入 MySQL |
| **角色闭环** | 只有 AI ↔ 用户 | **患者 → AI 预问诊 → 病历生成 → 医生诊断 → 评分反馈**，完整业务 SOP |
| **知识范围** | 通用训练数据，无实时医学知识 | **RAG 增强**：Pinecone 向量数据库 + text-embedding-v3 注入专属医学知识 |
| **数据安全** | 对话数据上传至第三方平台 | 数据自控，后端可私有化部署，满足医疗数据合规要求 |
| **可定制性** | 仅 Prompt 层面 | **代码层面**：SystemPrompt 角色定义 + Tool 工具链 + 检索策略 + 阈值调优 |
| **工作流编排** | 无 | AI 不是终点，而是流程起点——AI 生成病历 → 分配给医生 → 医生诊断 → 相似病例推荐 → 患者评分 |
| **可扩展性** | 无 | 可接入多模型（通义千问 / DeepSeek / 本地 Ollama）、多数据源、多业务规则 |

### 核心论点（面试口述一句话版）

> "通用 AI 是一个**对话工具**，我的系统是一个**业务流程平台**。区别在于：AI 在我的系统里不是终端产品，而是被编排在工作流中的一个环节——它负责把非结构化的患者口语转成结构化病历，然后自动入库、分配医生、辅助诊断。**AI 是引擎，业务流程是底盘。**"

## 三、简历项目描述（精炼通用版）

### 技术栈

```
后端：Spring Boot 3 + MyBatis + MySQL + MongoDB + LangChain4j + 通义千问(Qwen-Max) + Pinecone
前端：Vue 2 + Element UI + ECharts + Axios
```

### 项目简介（~120 字，可直接放入简历）

> **易诊通 —— AI 驱动的智能在线问诊平台**
>
> 从 0 到 1 独立设计并开发的全栈智能医疗系统，覆盖患者在线问诊、AI 预问诊对话、结构化病历自动生成、医生诊断开方、医患沟通、数据统计分析全流程。核心技术亮点：(1) 基于 **LangChain4j + 通义千问**实现 LLM 业务集成，通过 **Function Calling** 让 AI 在对话中自动调用后端接口生成病历入库；(2) 基于 **Spring WebFlux + SSE** 实现 AI 流式对话，前端 ReadableStream 逐字渲染；(3) 基于 **Pinecone 向量库 + text-embedding-v3** 实现 RAG 医学知识检索增强；(4) 自实现基于 **Jaccard 相似系数**的历史诊断推荐算法，辅助医生决策；(5) MySQL + MongoDB **混合数据架构**，关系型数据与文档型数据各取所长。

## 四、技术竞争力矩阵

每个技术点不仅要能说出"做了什么"，更要能说出**为什么这么做**和**对比过什么方案**。

| 技术点 | 实现方式 | 设计决策（为什么这么做？） | 对比过的方案 |
|--------|---------|----------------------|------------|
| **LLM 框架** | LangChain4j `@AiService` 声明式代理 | Java 技术栈统一，`@Tool` 注解零侵入集成业务方法，避免手写 HTTP + JSON 解析 | Python LangChain（跨语言调用复杂）、Spring AI（当时生态不如 LangChain4j 成熟）、原生 HTTP SDK（重复造轮子） |
| **流式响应** | Spring WebFlux `Flux<String>` + SSE | AI 生成 10s+，同步阻塞会耗尽线程池；响应式模型一个请求不占一个线程 | Tomcat Servlet AsyncContext（能用但编程模型重）、WebSocket（双向通信过度设计，SSE 更轻量） |
| **对话记忆** | MongoDB `MessageWindowChatMemory` | 文档模型天然匹配对话结构，单次查询取全量历史，Schema 灵活支持多种消息类型 | MySQL JSON 列（查询和更新对话数组效率低）、Redis（全内存成本高、持久化需额外设计） |
| **RAG 检索** | Pinecone + text-embedding-v3 | 全托管免运维，官方 LangChain4j 集成开箱即用，免费额度满足当前规模 | Milvus（需自运维）、pgvector（需额外 PostgreSQL 实例）、Elasticsearch（全文检索非语义检索） |
| **Function Calling** | `@Tool` 注解 + SystemPrompt 触发规则 | 让 AI 从"聊天机器人"升级为"业务操作入口"，对话中自动完成数据库写入 | 对话后解析文本提取参数（不准且不可靠）、固定表单提交（失去对话灵活性） |
| **诊断推荐** | Jaccard 相似系数 + IK 分词 | 无需训练数据、结果可解释（推荐理由 = 共享关键词）、冷启动友好 | Embedding 语义相似度（需额外 API 调用成本）、协同过滤（冷启动无数据） |
| **数据分层** | MySQL（业务） + MongoDB（AI 记忆） | 业务数据强 Schema 需事务支持走 MySQL，AI 对话半结构化走 MongoDB，各取所长 | 全 MySQL（对话存 JSON 列，读写效率低）、全 MongoDB（业务数据事务弱） |
| **前端工程化** | Axios 拦截器 + CancelToken + 缓存 Map | 路由切换自动取消请求避免竞态，重复请求去重减少服务端压力，客户端缓存降低加载延迟 | React Query / SWR（Vue 2 生态不支持）、无缓存（每次请求都加载，体验差） |

### Q1：简单介绍一下这个项目？

**考察点**：结构化表达能力、对项目的理解深度、是否真正参与核心设计。

**回答策略**：用"问题 → 方案 → 亮点 → 成果"四段式，控制在 2 分钟内。

**参考回答**：

> 我做的项目叫"易诊通"，是一个**AI 驱动的智能在线问诊平台**。
>
> **出发点**：传统在线问诊有个效率瓶颈——患者不是学医的，描述病情很口语化，医生需要反复追问基础信息才能做判断。我就在想，这个"追问基础信息"的环节能不能用 AI 替代？
>
> **核心方案**：在医患之间插入一层 AI 预问诊。患者先和 AI 助手对话，AI 按照 SystemPrompt 设定的医学问诊逻辑引导患者描述病情，把"肚子疼"转成"上腹部绞痛、进食后加重、持续 3 天"这样的专业表述，然后**自动生成结构化病历入库并分配医生**。医生拿到的不是原始聊天记录，而是一份半成品病历，可以直接进入诊断环节。
>
> **技术上我做了几个比较有深度的设计**：
> 1. AI 不是独立聊天，而是通过 **Function Calling** 和业务系统打通——对话中自动调用后端接口写库，生成真实病历；
> 2. 对话是**流式返回**的，Spring WebFlux + SSE，前端逐字渲染，体验对标 ChatGPT；
> 3. 加了 **RAG 检索增强**，用 Pinecone 向量库存医学知识，AI 回答前先检索相关内容作为上下文，减少幻觉；
> 4. 医生写诊断时，系统用 **Jaccard 相似系数**匹配历史相似病例，推荐处方和治疗方案作为参考。
>
> 整个项目从需求分析、数据库设计、接口定义到前后端开发都是**我个人独立完成**的，代码量在 8000+ 行左右（前后端合计），目前是完整可运行的状态。

**如果面试官追问"你写了多少代码"**：
> 前后端合计大约 8000+ 行。后端约 5000 行 Java（Controller + Service + Mapper + Config + AI Agent），前端约 3000+ 行（Vue 组件 + API 层 + 工具函数），外加 MyBatis XML 映射文件和配置文件。

### Q2：为什么选择 LangChain4j？和直接调 HTTP API 有什么区别？

**考察点**：技术选型判断力、对 LLM 应用架构的理解、对比分析能力。

**回答策略**：先说直接调 API 的痛点（证明你确实理解底层），再说框架解决了什么（证明你有选型思考），最后提一下对比过的替代方案。

**参考回答**：

> 如果直接调通义千问的 HTTP API，我需要手写至少 5 件事：
> 1. **Prompt 模板管理**：SystemPrompt + UserMessage 拼接，变量替换
> 2. **对话记忆管理**：维护消息列表、控制上下文窗口大小、持久化记忆
> 3. **Function Calling 解析**：定义 JSON Schema、解析 LLM 返回的 tool_call、执行完再把结果拼回对话
> 4. **流式响应解析**：SSE 协议的 `data:` 前缀去除、`[DONE]` 结束标记处理
> 5. **RAG 检索集成**：调用 Embedding API → 存向量 → 检索 → 拼回 Prompt
>
> 这些代码和业务无关，属于 LLM 应用的 boilerplate。LangChain4j 帮我抽象掉了这些：
> - 定义 `@AiService` 接口 + `@SystemMessage` 注解，框架自动生成代理实现，零手写 HTTP
> - `@Tool` 注解一个普通 Java 方法，LLM 就能在对话中调用，框架自动处理 JSON Schema 生成和结果回传
> - `MessageWindowChatMemory` 开箱即用，我只需实现 `ChatMemoryStore` 接口对接 MongoDB
> - RAG 的 Pinecone + Embedding 集成一行配置搞定
>
> **对比过的替代方案**：
> - **Python LangChain**：生态最成熟，但我的后端是 Java 技术栈，跨语言 RPC 调用会增加延迟和复杂度
> - **Spring AI**：Spring 官方出品，但立项时版本还比较早期，文档和社区都不如 LangChain4j
> - **原生 HTTP SDK**：最灵活，但等价于把 LangChain4j 的核心功能重新实现一遍
>
> 本质上这是一个"**买 vs 造**"的决策。LangChain4j 覆盖了我的需求面 80%+，剩下的 20%（如自定义记忆持久化策略）通过实现其扩展接口就能完成，ROI 很高。

### Q3：流式响应具体怎么实现的？WebFlux 和传统 Tomcat 同步模型有什么区别？

**考察点**：响应式编程理解、并发模型认知、SSE 协议熟悉度。

**回答策略**：先讲"为什么不能用同步模型"（建立问题意识），再讲技术实现链路（证明动手能力），最后提一个细节亮点（展示工程思维）。

**参考回答**：

> **为什么要用响应式模型**：传统 Spring MVC 是 **Thread-per-Request** 模式——一个 HTTP 请求绑定一个 Tomcat 线程，直到响应完成才释放。AI 生成一次回复可能需要 10-20 秒，如果 200 个患者同时在线问 AI，Tomcat 默认 200 线程的线程池直接打满，后续请求全部排队。而实际上这 10 秒里线程大多在等 AI API 返回，CPU 是完全空闲的——线程被白白阻塞了。
>
> **我的实现链路**：
> ```
> 通义千问 API (SSE 流) → LangChain4j TokenStream → WebFlux Flux<String> → SSE → 浏览器 Fetch ReadableStream → 逐字渲染
> ```
> - 后端：Controller 返回 `Flux<String>`（`text/event-stream`），每收到一个 token 就 `onNext` 推送
> - 前端：用 Fetch API 的 `ReadableStream` 消费 SSE 流，拿到一个字符就 `append` 到页面上
> - 做了一点体验优化：对标点符号（，。！？）做了**人工延迟**（约 50-80ms），模拟自然的停顿感，避免逐字效果变成"一口气吐完"
>
> **关于模型选型**：实际上因为依赖关系，跑的还是 Tomcat 容器，但关键是用了 WebFlux 的编程模型——返回 `Flux` 后 Tomcat 走 Servlet 3.1 的 AsyncContext，线程立即释放回池，数据到达时由 IO 线程回调推送。所以**线程不会阻塞等待**。

**追问**："WebFlux 和 Spring MVC 能共存吗？"
> 可以。我这个项目就是混合模式——普通 REST 接口走 MVC，AI 流式接口走 WebFlux（返回 `Flux` 类型）。Spring 会根据返回值类型自动选择处理模型。如果要纯 WebFlux（Netty 容器），需要确保整个调用链都是非阻塞的，包括数据库驱动（MySQL 的 JDBC 是阻塞的，需要换 R2DBC），对我来说当前方案性价比最高。

### Q4：Function Calling 具体是怎么设计的？AI 凭什么能"操作"你的数据库？

**考察点**：LLM 应用设计深度、业务集成能力、Prompt Engineering 功底。

**回答策略**：先讲 Function Calling 的技术原理（证明你理解底层），再讲你的 SystemPrompt 怎么设计触发规则（证明你有工程化思维），最后点出一个关键风险及应对。

**参考回答**：

> Function Calling 的本质是**让 LLM 通过 JSON 协议调用外部函数**，把 AI 从"对话引擎"升级为"业务操作入口"。
>
> **技术流程**：
> 1. 我定义了一个 `AgentTools` 类，用 LangChain4j 的 `@Tool` 注解标记了 `upLoadRecord` 方法，参数包括姓名、性别、年龄、主诉、过敏史、既往史等
> 2. 框架启动时扫描 `@Tool` 注解，生成对应的 JSON Schema 注册到 LangChain4j 的 ToolRegistry
> 3. 每次 AI 对话请求时，LangChain4j 把可用工具的 Schema 列表发给 LLM
> 4. LLM 判断需要调用工具时，返回 `tool_calls` JSON（含函数名 + 参数值），LangChain4j 自动反序列化 → 反射调用 Java 方法 → 执行结果回传给 LLM → LLM 基于结果生成自然语言回复
>
> **Prompt 工程——触发规则设计**：
> 我 SystemPrompt 里定义了明确的条件：AI 必须收集齐"姓名、性别、年龄、联系方式、主诉"5 个必填项后，才可以调用 `upLoadRecord`。我还在提示词中要求 AI 先做**信息确认**——收集完后整理成病历格式让患者确认，确认无误再触发工具调用。这样防止 AI 在信息不全时"自作主张"创建不完整的病历。
>
> **踩过的坑**：早期 LLM 偶现"幻觉调用"——即使用户没说相关信息，AI 也编造参数去调用工具。我的应对是：(1) SystemPrompt 中加约束"只基于用户已提供的信息填充参数，缺失字段必须询问而非猜测"；(2) Service 层做了参数校验，必填字段为空直接拒绝并返回提示。

### Q5：RAG 是怎么实现的？为什么用 Pinecone？

**考察点**：检索增强生成的理解、向量数据库认知、技术选型。

**回答策略**：先讲 RAG 要解决什么问题（建立动因），再讲完整链路，最后做技术对比。

**参考回答**：

> **RAG 解决的问题**：LLM 的知识有截止日期，且通用模型对细分医学领域知识覆盖不足。直接问它一个具体用药方案，可能给出过时或不够精准的回答。RAG 的思路是：**先检索相关知识，拼到 Prompt 里，让 LLM 基于检索结果回答**——相当于给 LLM 现场翻书。
>
> **我的实现链路**：
> ```
> 医学知识文档 → text-embedding-v3 → 向量 → Pinecone (medicine-index)
> 用户问题 → embedding → Pinecone 相似度检索 (cosine similarity) → 结果存入 ChatMemory → LLM 参考回答
> ```
> - Embedding 模型选了阿里云的 `text-embedding-v3`，和对话模型同一生态，延迟最低
> - 检索参数：相似度阈值 0.8（低于 0.8 认为"知识库中无相关内容"，不拼入 Prompt，避免噪声干扰 LLM），Top-1 返回（当前知识库规模小，取最相关一条即可）
> - 检索结果写入 `UserMessage` 的上下文，随对话历史一起发给 LLM
>
> **为什么用 Pinecone**：
> - 全托管，零运维负担——不需要自己搭索引服务
> - 官方 LangChain4j 集成，`@Inject` 即可使用
> - 免费额度（1 个 index + 10 万向量）对当前项目规模绰绰有余
>
> **如果规模扩大**，我会考虑：
> - **Milvus**：开源向量库，支持私有化部署，适合医疗数据合规要求
> - **pgvector**：如果项目已经用 PostgreSQL，直接在数据库内做向量检索，减少架构复杂度
> - **Elasticsearch + 同义词词典**：关键词检索 + 语义检索混合，覆盖更多查询场景

### Q6：诊断推荐算法具体怎么做的？为什么不用更复杂的方法？

**考察点**：算法设计思维、工程实用性判断、对"过度设计"的警觉。

**回答策略**：先讲算法逻辑，再讲"为什么不做更复杂的方案"（这是加分项，展示你有工程成本意识）。

**参考回答**：

> 医生在输入诊断结果时，系统会用 **Jaccard 相似系数**匹配历史已完成诊断的病例，推荐相似的治疗方案作为参考。
>
> **算法流程**：
> 1. 医生输入的诊断文本用 IK 分词器分词
> 2. 和历史已完成诊断的文本分别计算 Jaccard 系数：`J(A,B) = |A∩B| / |A∪B|`
> 3. 相似度超过阈值的病例，连带其处方和医嘱一起返回给前端展示
>
> **为什么不用更复杂的方法**：
> - 这个阶段数据量不大（假设几百到几千条诊断记录），Jaccard 的 O(n) 扫描完全够用
> - **可解释性**：推荐理由可以展示为"匹配关键词：上呼吸道感染、发热、咳嗽"，医生一眼就懂推荐逻辑，信任度高
> - **冷启动友好**：不需要历史行为数据（协同过滤做不了），不需要标注数据（监督学习做不了）
> - **Embedding 语义相似度**：确实能解决"腹痛 vs 肚子疼"的同义问题，但我没选的原因是：(1) 每次诊断都要调 Embedding API，增加延迟和成本；(2) 医学文本中的同义词泛化反而有风险——"急性腹痛"和"慢性腹痛"语义向量非常接近，但临床处理完全不同
>
> **如果要优化**，我会走**混合方案**：IK 分词 + 医学同义词词典做第一轮召回（保证召回率），Embedding 相似度做第二轮精排（保证准确率），两层漏斗比单纯用一种方案效果好。

### Q7：密码安全你是怎么处理的？硬编码的密钥安全吗？

**考察点**：安全意识、能否反思自己的设计、诚实度。

**回答策略**：诚实承认当前设计的不足，展示你知道正确的做法，给出改进方案。

**参考回答**：

> 当前实现是前端 AES-128-CBC 加密，密钥 `"Deng200301094060"` 直接写在前端代码里，后端解密后和数据库比对。
>
> 坦诚讲，这个方案在生产环境下**不够安全**——密钥硬编码在前端 JS 中，任何人打开浏览器 DevTools 就能拿到，本质上只是让密码在 HTTP 报文中不可读，但不是真正的安全。
>
> **生产环境标准做法**：
> 1. **全站 HTTPS**：通过 TLS 1.3 保护传输层安全，前端不需要也不应该自己加密密码
> 2. **后端 BCrypt 哈希存储**：密码只存不可逆的哈希值（含盐），验证时比较哈希而非解密
> 3. **JWT 无状态认证**：替代当前 session-based 方案，更适合前后端分离架构
> 4. **接口防护**：登录接口加限流（防暴力破解）、密码复杂度校验、异常登录告警
>
> 这个项目目前是学习和演示用途，所以做了 AES 加密来**展示密码安全的设计意识**。如果是真实生产系统，我会在第一版就用 BCrypt + HTTPS + JWT。

**面试加分点**：主动说出当前设计的不足 + 准确的改进方案，比死守"这个设计没问题"好得多。

### Q8：为什么 MySQL 和 MongoDB 混用？怎么决定什么数据放哪里？

**考察点**：数据建模能力、多数据库实践经验、技术选型的 trade-off 思维。

**回答策略**：从数据特征出发做选型决策，而非"为了用而用"。

**参考回答**：

> 简单原则：**看数据的"形状"和"读写模式"**。
>
> **MySQL（关系型）** 存的：患者、医生、病历、诊断、评论、回复。这些数据特征：
> - Schema 固定（表的字段明确，不会频繁变化）
> - 强关联（病历关联患者 + 医生 + 诊断，需要 JOIN 查询）
> - 需要事务（病历创建 + 状态更新要保证原子性）
>
> **MongoDB（文档型）** 存的：AI 对话消息。它的特征：
> - 半结构化（系统消息、用户消息、AI 消息、工具调用消息，结构各异）
> - 读写模式是"按会话 ID 取全部消息"——一个 session 的消息天然适合存成嵌套文档，一次查询拿到完整对话链
> - Schema 灵活——以后加"图片消息""语音消息"类型不需要 ALTER TABLE
>
> **这个决策在实际生产中也常见**——MySQL 做业务主库，MongoDB/Redis/ES 做特定场景的数据存储，各取所长。关键是不为了"用新技术"而强行引入复杂度：我这个项目里 MongoDB 只存对话，出问题不影响核心业务流程。

**追问**："如果只用 MySQL 存对话，会有什么问题？"
> 可以存，用 JSON 列。但问题在于：对话是一个数组，每次新增消息需要读出来 → append → 写回去，并发场景下容易丢消息。MongoDB 的 `$push` 操作是原子的，天然支持追加。另外查询"某个会话的全部消息"在 MongoDB 里是一个 O(1) 的文档查询，在 MySQL 里如果消息拆成行就需要 `SELECT * WHERE session_id = ?`，数据多了需要索引优化。

### Q9：这个项目如果让你现在重新做，会做哪些改进？

**考察点**：技术成长、自我反思、是否了解业界更优方案。

**回答策略**：从架构、安全、AI、工程化四个维度各挑 1-2 点，每个点要有"当时怎么做 → 为什么 → 现在怎么做 → 为什么更好"的思考链。

**参考回答**：

> **架构层面**：
> - 当时：单体应用，所有模块在一个 Spring Boot 项目中
> - 现在：仍然支持单体起步（单体不是原罪），但会按领域做模块化分包（patient / doctor / record / agent），包内高内聚、包间接口通信。如果团队 3 人以上且模块独立迭代需求明确，再考虑拆微服务

### Q10：项目中遇到的最大挑战是什么？怎么解决的？

**考察点**：问题解决能力、技术深度、能否复盘总结。

**回答策略**：选一个最有代表性的问题，按"问题背景 → 为什么难 → 我的解决思路 → 效果"展开。推荐选"AI 对话记忆管理"或"Function Calling 可靠性"。

**推荐回答：Function Calling 的"幻觉调用"问题**

> **问题背景**：AI 在对话中偶现"用户还没提供完整信息，AI 就自行编造参数调用工具创建病历"。比如用户只说了"我头痛"，AI 就调用 `upLoadRecord` 把姓名填成"未知"、年龄填成"30"——这导致数据库中出现无效病历。
>
> **为什么难处理**：这本质上是 LLM 的幻觉问题，无法 100% 消除，只能通过多层防护把概率降到可接受范围。
>
> **我的解决思路（三层防线）**：
> 1. **Prompt 层**：SystemPrompt 中明确规定"必须收集齐姓名、性别、年龄、联系方式、主诉 5 个必填项后才能调用工具，缺失任何一项必须继续询问用户"
> 2. **应用层校验**：`AgentTools.upLoadRecord` 方法内部对所有必填参数做 null/空字符串检查，不符合要求时返回明确错误信息给 LLM："请补充以下缺失信息：姓名、年龄"，LLM 收到后会继续向用户询问
> 3. **数据库层**：关键字段设置 NOT NULL 约束，作为最后兜底
>
> **效果**：三层防护后，无效病历创建率从偶发降到基本为 0。这个经历让我深刻理解了"**在 LLM 应用中，永远不要 100% 信任 AI 的输出，必须在代码层做校验**"。

**备选回答：AI 对话记忆的上下文窗口管理**

> **问题**：Qwen-Max 有 token 上限，对话越长，上下文越接近限制。我需要在"给足上下文"和"不超限"之间找平衡。
>
> **解决**：
> 1. `MessageWindowChatMemory` 窗口设为最近 20 条（约 3000-4000 token），留足余量给 RAG 检索结果和 SystemPrompt
> 2. 记忆持久化到 MongoDB，用户刷新页面或换设备也能恢复对话
> 3. SystemPrompt 中引导 AI 在对话中期"总结患者核心信息"，减少后续对话对原始消息的依赖
>
> **引申思考**：更好的方案是"滑动窗口 + 摘要"——旧消息自动压缩成摘要保留，既省 token 又不丢关键信息。这是 LangChain4j 的 `MessageWindowChatMemory` 当前不支持的，如果要实现需要自定义 `ChatMemoryStore`。

### Q11（新增）：你这和直接问通义千问 / ChatGPT 有什么区别？为什么不直接用现成的 AI 聊天？

**考察点**：项目核心价值的理解、对比分析能力、是否思考过"为什么需要你"。

> 这是项目介绍的"灵魂拷问"，面试官一定会问到。详细对比见本文档**第二章的对比表**。

**回答策略**：一句话定调 + 三点展开 + 总结收束。

**参考回答**：

> **一句话定调**：通用 AI 是"对话工具"，我的系统是"业务流程平台"——区别在于 AI 在我的系统里不是最终产品，而是嵌入工作流的一个环节。
>
> **三点展开**：
> 1. **业务闭环**：直接问 AI，对话结束就结束了。我的系统里对话是起点——AI 生成病历 → 入库 → 分配医生 → 医生写诊断 → 推荐历史病例 → 患者评分。这是一条完整 SOP，AI 只负责最前面的"信息采集和结构化"这一环。
> 2. **系统集成**：AI 通过 Function Calling 直接操作后端的 MySQL 数据库，创建真实病历记录——这不是"AI 替你写一段文字"，而是"AI 替你完成了一次业务操作"。通用聊天 AI 做不了这个。
> 3. **领域增强**：通过 RAG 注入医学专属知识，通过 SystemPrompt 定义医疗问诊 SOP，通过 Tool 链限制 AI 只能做"病历收集"这一件事。这些都是直接问通用 AI 做不到的——通用 AI 不会按你的业务流程走。
>
> **总结**：你当然可以直接打开通义千问问病情，但问完之后呢？信息散落在聊天记录里，你得自己去挂号、自己跟医生再说一遍。我的系统把这个问题解决了——**AI 负责采集和结构化，医生负责专业判断，系统负责流程编排**。这叫"AI + 业务流程"，不叫"AI 聊天"。

## 六、深挖方向 & 准备建议

| 方向 | 可能追问 | 准备要点 |
|------|---------|---------|
| **并发性能** | "1000 个病人同时和 AI 聊天，系统扛得住吗？" | AI API 有并发限制（通义千问默认 QPS 限制），需要客户端做排队/限流/降级；Tomcat 线程池 + Reactor 的并发模型差异 |
| **LLM 幻觉** | "AI 给错医疗建议导致医疗事故怎么办？" | SystemPrompt 加免责声明、RAG 减少幻觉、Function Calling 校验层、人工审核兜底、拒绝回答超范围问题 |
| **数据一致性** | "Function Calling 写到一半数据库挂了怎么办？" | 了解本地事务（当前方案）、分布式事务 TCC/SAGA（演进方案）、幂等设计、重试机制 |
| **Prompt Engineering** | "你的 SystemPrompt 是怎么设计的？迭代了几版？" | 熟读自己的 `SystemPrompt.txt`，能说出角色定义 → 能力描述 → 流程规则 → 约束条件的设计逻辑 |
| **模型选型** | "为什么选通义千问而不是 GPT-4/DeepSeek/文心一言？" | 国内访问稳定性、中文医疗理解能力、API 成本（约 0.04 元/千 token）、阿里云生态一致性 |
| **Token 成本** | "一次 AI 对话大概消耗多少 token？成本多少？" | 估算：SystemPrompt ~500 token + 对话 ~3000 token/轮，平均一次问诊 5000-8000 token，按 Qwen-Max 定价约 0.2-0.3 元/次 |
| **向量检索** | "为什么阈值设 0.8？换成 0.6 会怎样？" | 阈值要平衡召回率和准确率——0.8 可能漏掉相关但表述不同的内容，0.6 可能引入噪声。需要根据实际检索效果调参 |
| **AI 测试** | "AI 的功能你怎么测试？能自动化吗？" | 诚实说当前主要靠人工测试。自动化方向：固定输入 → 检查 Function Calling 是否触发、参数是否正确、输出是否含特定关键词——类似于 LLM 的 assertion-based 测试 |

6. **不要说"这是课程项目/练手项目"**：说"个人独立设计并开发的全栈项目"。客观上它就是独立完成的，这不是撒谎
