# 诊易通（YZT-Medicine）项目业务逻辑详细梳理

---

## 一、项目概述

**诊易通**是一个在线智能医疗问诊平台，核心功能是连接患者与医生，并通过 AI 大模型（阿里云百炼 qwen-max）辅助完成病例提交、智能导诊、诊断推荐等医疗流程。

- **后端**: Spring Boot 3.5.0 + MyBatis 3.0.3 + MySQL 8.x
- **前端**: Vue 2.x + Vue Router + Vuex + Element UI
- **AI 层**: LangChain4j 1.0.0-beta3 + 阿里云百炼 DashScope
- **向量数据库**: Pinecone (AWS us-east-1)
- **会话存储**: MongoDB (Chat Memory)
- **JDK**: 1.8（与 Spring Boot 3.5.0 不兼容，实际需 Java 17+）

## 三、核心业务模块详解

### 模块一：认证管理（Auth）

**涉及文件：**
- Controller: `AuthController.java` → `/auth`
- Service: `PatientService.java` / `DoctorService.java`（登录/注册方法）
- Mapper: `PatientMapper.java/xml` + `DoctorMapper.java/xml`（认证查询）

**设计说明：** 无独立 user 表。患者登录凭证（username/phone/email/password）存储在 `patient` 表，医生登录凭证存储在 `doctor` 表。统一认证入口 `/auth/login` 依次查询两表。

**用户角色体系：**

| role值 | 角色 | 说明 |
|--------|------|------|
| 0 | 患者 (Patient) | 可提交病例、查看诊断、评论交流 |
| 1 | 医生 (Doctor) | 可查看病例、给出诊断、回复评论 |

**业务功能：**

| 功能 | API | 说明 |
|------|-----|------|
| 患者注册 | `POST /patient/register` | 接收 patientName, username, password, phone, email 等，写入 patient 表 |
| 医生注册 | `POST /doctor/register` | 接收 doctorName, username, password, phone, email, cityName 等，写入 doctor 表 |
| 统一登录 | `POST /auth/login` | 以 identity（手机号）+ password 分别在 patient 和 doctor 表中匹配，返回统一格式 `{userId, username, phone, email, role}` |
| 修改资料 | `POST /auth/update` | 根据 role 更新 patient 或 doctor 表的账号信息 |
| 找回密码 | `GET /auth/findPassword` | 输入手机号，分别在 patient/doctor 表中查找，返回对应 ID |

**密码加密方案：**
- 前端使用 `crypto-js` AES 加密后传输
- 后端 `PasswordUtil.java` 使用 `AES/CBC/NoPadding` 模式解密
- 密钥/IV 硬编码：`Deng200301094060`

**登录查询逻辑（AuthController.java）：**
```
POST /auth/login {identity: "手机号", password: "加密密码"}
  → 先查 patient 表: SELECT * FROM patient WHERE phone=? AND password=?
  → 匹配成功 → 返回 {userId: patientId, username: patientName, phone, email, role: 0}
  → 未匹配 → 再查 doctor 表: SELECT * FROM doctor WHERE phone=? AND password=?
  → 匹配成功 → 返回 {userId: doctorId, username: doctorName, phone, email, role: 1}
  → 均未匹配 → 返回错误码 2003
```

**关键 SQL：**

```sql
-- UPSERT：插入或更新医生信息
INSERT INTO doctor (doctorName, username, password, phone, email, cityName, hospitalName, departmentName, introduction)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)
ON DUPLICATE KEY UPDATE
    doctorName = VALUES(doctorName),
    cityName = VALUES(cityName),
    hospitalName = VALUES(hospitalName),
    departmentName = VALUES(departmentName),
    introduction = VALUES(introduction)
```

该设计使得创建和更新使用同一个接口，在 doctor 表的 userId 唯一键上实现"存在则更新、不存在则插入"。

**分页查询参数流：**
1. 前端传 `DoctorDTO`（含 page, pageSize, cityName, hospitalName, departmentName）
2. Service 计算 `offset = (page - 1) * pageSize`
3. 两次 SQL：`selectDoctorList` 取分页数据 + `countDoctorList` 取总数
4. 返回 `{total: N, doctorList: [...]}`

**病历状态流转：**

```
  (患者提交)                         (医生填写中)                           (可评分、可评论)
```

**业务功能：**

| 功能 | API | 说明 |
|------|-----|------|
| 创建病历 | `POST /record/add` | 验证 phone 不为空，写入 record 表，status 默认=1 |
| 分页查询 | `POST /record/page` | 支持按 status（逗号分隔多值）、patientId、doctorId 筛选 + 分页 |
| 病历详情 | `GET /record/{recordId}` | 查 record + LEFT JOIN doctor，并附带关联的 Diagnostic |
| 更新病历 | `POST /record/update` | **关键事务**：同时更新 record 状态 + 插入/更新诊断信息 |
| 诊断推荐 | `POST /record/recommend` | 基于 Jaccard 相似度的诊断推荐 |

**`POST /record/update` 核心事务逻辑（RecordServiceImpl.java:64-85）：**

```
@Transactional
update(Record record):
  1. 如果 record.status == 2（已诊断）且 diagnostic 不为空：
     a. 将 recordId 设入 diagnostic 对象
     b. 查询是否已有诊断记录（diagnosticMapper.queryDiagnosticById）
     c. 存在 → updateDiagnostic（更新诊断）
     d. 不存在 → insertDiagnostic（插入新诊断）
  2. 更新 record 表的 status 和 score
```

这个设计使得医生在状态2下可以反复修改诊断，状态变为3（已完成）后诊断就固定了。

**分页查询的筛选逻辑（RecordMapper.xml:14-52）：**
- `status` 参数支持逗号分隔（如 "1,2,3"），SQL 中用 `IN` 子句
- `doctorId` 对 `d.doctorId` 过滤（医生看自己的病例）
- `patientId` 对 `r.patientId` 过滤（患者看自己的病例）
- `countRecordList` 额外支持 patientName 和 doctorName 模糊搜索

**注意：** `RecordQueryDTO.doctorId` 类型是 `String`，但数据库中是 `Integer`，实际传参时存在类型不匹配隐患。

#### 5.2 相似诊断推荐（核心算法）

**API:** `POST /record/recommend`
**请求参数:** `{diagnosisText: "患者症状描述", limit: 5}`

**算法流程（DiagnosticServiceImpl.java:32-86）：**

```
1. 获取所有已完成诊断（status=3）
   └── SQL: 三表 JOIN（diagnostic + record + doctor），取 result, score, docName 等

2. 文本预处理 (preprocessText)
   ├── 转小写
   ├── 去除标点符号（\\p{P}\\p{S}）
   └── 合并多余空格

3. 关键词提取 (extractKeywords)
   ├── 按空格分词（split("\\s+")）
   ├── 过滤长度 ≤ 1 的词
   └── 过滤停用词（的、了、和、与... 共 20 个中文停用词）

4. Jaccard 相似度计算
   J(A, B) = |A ∩ B| / |A ∪ B|
   └── 过滤相似度 ≤ 0.1 的结果

5. 排序规则
   第一关键字：相似度降序
   第二关键字：患者评分（score）降序（null 排最后）

6. 返回前 limit 条
```

**算法局限：**
- 中文分词使用 `split("\\s+")` 按空格切分，对中文无效（中文词之间无空格），导致整句被当作一个 token
- 停用词表仅 20 个，覆盖不足
- 全表扫描所有已完成诊断，数据量大时性能差
- Jaccard 对词频不敏感，两个包含相同关键词但语义相反的诊断可能得到高相似度

### 模块六：AI 智能聊天（Agent）—— 项目亮点

**涉及文件：**

**这是整个项目最复杂的模块，整合了 LLM 对话、Function Calling、RAG 检索、会话记忆四项 AI 工程能力。**

#### 6.1 AI 对话架构

```
前端 (Vue)
  │ POST /agent/chat  {memoryId, message}
  │ Content-Type: text/stream;charset=utf-8
  ▼
AgentController
  │ agentAssistant.chat(memoryId, message)
  ▼
AgentAssistant (@AiService 接口)
  │ ┌─────────────────────┐
  │ │ SystemPrompt.txt    │  系统提示词（定义"医疗小易"人设）
  │ └─────────────────────┘
  │ ┌─────────────────────┐
  │ │ ChatMemoryProvider  │  会话记忆（最近 20 轮对话）
  │ │ → MongoDB 持久化     │
  │ └─────────────────────┘
  │ ┌─────────────────────┐
  │ │ AgentTools          │  Function Calling（提交病例）
  │ └─────────────────────┘
  │ ┌─────────────────────┐
  │ │ ContentRetriever    │  RAG 向量检索（Pinecone）

  │
  ▼

  │ 返回: SSE 流式响应
  ▼

```

#### 6.2 配置解析

**CommonConfig.java —— 两个核心 Bean：**

1. **ChatMemoryProvider（会话记忆）：**
```java
MessageWindowChatMemory.builder()
    .maxMessages(20)       // 保留最近 20 条消息
    .chatMemoryStore(memoryStore)  // 持久化到 MongoDB
    .build();
```

2. **ContentRetriever（RAG 检索增强）：**
```java
EmbeddingStoreContentRetriever.builder()
    .embeddingStore(embeddingStore)   // Pinecone
    .embeddingModel(embeddingModel)   // text-embedding-v3
    .maxResults(1)      // 只返回最匹配的 1 条
    .minScore(0.8)      // 相似度阈值 0.8

```

**EmbeddingStoreConfig.java —— Pinecone 向量库：**
- 索引名: `medicine-index`
- 命名空间: `medicine-namespace1`
- 云平台: AWS us-east-1
- 向量维度: 自动从 embeddingModel 获取（text-embedding-v3 通常为 1024 维）

#### 6.3 Function Calling（AgentTools.java）

**工具定义：**
```java
@Tool(name = "提交病例", value = "根据参数，在确保所需数据通过对话得到后，为用户执行病例的提交")
public String upLoadRecord(Record record)
```

**工作流程：**
```
AI 对话中患者说"我要看病"
  → LLM 判断需要调用"提交病例"工具
  → LLM 从对话中提取 Record 参数（patientName, phone, description 等）
  → 自动调用 upLoadRecord(record) 方法：
      │
      ├── 1. 验证必填字段（patientName, phone）
      ├── 2. 设置 createTime = new Date()
      ├── 3. 通过 phone 查找已有用户
      │      ├── 找到 → 使用其 userId 作为 patientId
      │      └── 未找到 → 自动创建 User（密码 "123456"，role=0）
      ├── 4. 设置 status = 1（待诊断）
      └── 5. 调用 recordService.add(record) 写入数据库
  → 返回 "病例提交成功，病例ID: XX" 给 LLM
  → LLM 将结果友好地告知患者
```

**安全问题：** 自动创建患者时使用硬编码弱密码 `123456`。

#### 6.4 会话记忆（MemoryStore.java）

**MongoDB 存储方案：**
- 数据库: `chat_memory_db`
- 集合: `chat_messages`
- 文档结构:
```json
{
  "_id": ObjectId("..."),
  "memoryId": 1711000000000,  // 时间戳作为会话 ID
  "content": "[{\"type\":\"USER\",\"text\":\"...\"},{\"type\":\"AI\",\"text\":\"...\"}]"
}
```
- 操作: upsert（存在则更新，不存在则插入）
- `content` 字段存储序列化后的完整对话消息列表（JSON 格式）

**memoryId 生成：**
- `AgentController` 中：`memoryId = chatForm.getMemoryId() != null ? chatForm.getMemoryId() : System.currentTimeMillis()`
- 前端可传固定 memoryId 实现会话连续性，不传则每次新建会话

#### 6.5 SystemPrompt 设计（SystemPrompt.txt）

"医疗小易"人设包含 7 个方面：

| 维度 | 内容 |
|------|------|
| 身份定位 | 诊易通平台智能助手，医疗顾问 + 伴诊助手 |
| 医疗咨询 | 将口语化描述转为专业术语，分析病因/诊断/治疗/预防 |
| 核心功能 | AI 精准导诊 + AI 病例提交 |
| 病例流程 | 必填：姓名/性别/年龄/联系方式/主诉；选填：病史/过敏史/习惯 |
| 症状转化 | 模糊描述 → 专业表达（如"肚子痛"→"上腹部绞痛，进食后加重"） |
| 交流技巧 | 简洁明了、逻辑连贯、表情符号、表达同理心 |
| 边界控制 | 仅限医疗咨询，其他领域礼貌拒绝 |

**注意：** Prompt 末尾有 `{{current_date}}` 占位符，但代码中未做替换，实际发送给 LLM 的是原始模板字符串。

#### 6.6 Jackson 双 ObjectMapper 配置

项目配置了两套 Jackson ObjectMapper：

| Bean | 用途 | 特点 |
|------|------|------|
| `objectMapper` (@Primary) | Spring MVC 请求响应 | 标准配置 |
| `langChainObjectMapper` | LangChain4j 内部序列化 | 更宽松：接受单值当数组、空字符串当 null、未知枚举当 null |

这解决了 LangChain4j 在 JSON 反序列化时的兼容性问题（如 AI 返回的 JSON 格式不规范）。

### 模块七：评论与回复（Comment & Reply）

| 字段 | 类型 | 说明 |

| commentId | Integer | 主键 |
| userId | Integer | 评论者 ID |
| recordId | Integer | 所属病历 ID |

**Reply.java 结构：**

| 字段 | 类型 | 说明 |
|------|------|------|
| replyId | Integer | 主键 |
| commentId | Integer | 所属评论 ID |
| userId | Integer | 回复者 ID |
| role | Integer | 回复者角色 |

**关键 SQL：CommentMapper.xml 中使用了 MyBatis `<resultMap>` + `<collection>` 实现一对多映射：**

```xml
<resultMap id="commentWithRepliesMap" type="Comment">
    <id property="commentId" column="commentId"/>
    <!-- 评论字段... -->
    <collection property="replies" ofType="Reply">
        <id property="replyId" column="replyId"/>
        <!-- 回复字段... -->
    </collection>
</resultMap>
```

一次 LEFT JOIN 查询即获得"评论+其下所有回复"的嵌套结构。

**业务功能：**

| 查全部评论 | `GET /comment` | 管理功能 |

## 四、核心业务流程

### 流程一：患者 AI 问诊 + 提交病例

```
患者打开 AI 问诊页面
  │
  ├─ 1. 与"医疗小易"对话（SSE 流式响应）
  │     └── 每轮对话保存到 MongoDB（memoryId 标识会话）
  │
  ├─ 2. AI 引导收集信息：
  │     姓名、性别、年龄、联系方式、症状描述、病史、过敏史、生活习惯
  │
  ├─ 3. 信息齐全后，AI 自动触发 Function Calling
  │     └── AgentTools.upLoadRecord(record)
  │           ├── 通过手机号查找或创建 Patient
  │           ├── 设置 status=1（待诊断）
  │           └── 写入 record 表
  │
  └─ 4. AI 告知患者"病例提交成功"，并推荐科室/医生
```

### 流程二：医生接诊 + 诊断

```
医生登录 → 查看病历列表（status=1 待诊断）
  │
  ├─ 1. 查看病历详情（患者症状、病史等）
  │
  ├─ 2. 接诊（更新 status=2）
  │
  ├─ 3. 填写诊断信息：
  │     ├── result（诊断结果）
  │     ├── prescription（处方）
  │     └── orders（医嘱）
  │
  ├─ 4. 提交诊断（status=2 → 触发 @Transactional）
  │     ├── 插入或更新 diagnostic 表
  │     └── 更新 record 表 status
  │
  └─ 5. 完成诊断（status=3）
        └── 患者可查看、评分、评论
```

### 流程三：患者查看诊断 + 评分

```
患者登录 → 查看自己的病历列表
  │
  ├─ 1. 查看已完成诊断（status=3）
  │     └── 包含诊断结果、处方、医嘱、医生信息
  │
  ├─ 2. 评分（score 字段）
  │
  └─ 3. 评论交流
        └── 可与医生互动讨论
```

### 流程四：诊断推荐

```
医生或患者输入"症状描述"
  │
  ├─ 1. 调用 POST /record/recommend {diagnosisText, limit}
  │
  ├─ 2. 后端查询所有已完成诊断（三表 JOIN）
  │
  ├─ 3. Jaccard 相似度匹配
  │
  └─ 4. 返回 Top N 相似病例（含诊断结果、评分、医生信息）
```

## 六、技术实现要点

### 6.1 统一响应格式

所有 API 返回通过 `Result.java` 封装：

```json
// 成功
{"code": 200, "msg": "操作成功", "result": {...}}

// 失败
{"code": 2003, "msg": "账户或密码错误", "result": null}
```

错误码体系（`ResultEnum.java`）：
- `200`: 成功
- `201`: 失败
- `500`: 系统异常
- `1000`: 参数异常
- `2001`: Token 不合法（预留）
- `2002`: 无权限（预留）
- `2003`: 账户或密码错误

### 6.2 前端加密传输

```
前端 (web/src/utils/secret.js)
  │ crypto-js AES 加密
  │ 密钥: "Deng200301094060"
  │ 模式: AES/CBC/NoPadding
  ▼
后端 (PasswordUtil.java)
  │ 同密钥解密
  │ 解密后得到明文密码
  ▼
存入数据库（明文）
```

**安全风险：** 数据库存储明文密码，一旦泄露后果严重。建议改用 BCrypt 单向哈希。

### 6.3 SSE 流式输出（AI 聊天）

```
AgentController.chat()
  │ @PostMapping(value = "/chat")
  │ produces = "text/stream;charset=utf-8"
  │
  ▼
AgentAssistant.chat(memoryId, message)
  │ 返回类型: Flux<String>
  │ Spring WebFlux 响应式流
  ▼
浏览器通过 EventSource / fetch 逐字接收
```

前端流式解析（`web/src/utils/streamParser.js`）负责处理 SSE 数据流。

### 6.4 分页查询统一模式

所有分页查询遵循相同模式：
1. 前端传 `{page, pageSize, ...筛选条件}`
2. Service 计算 `offset = (page - 1) * pageSize`
3. 两次 SQL：查列表 + 查总数
4. 返回 `{total: N, recordList: [...]}`

### 6.5 日期处理

- `CustomDateDeserializer.java` 支持多种日期格式反序列化：
  - `yyyy-MM-dd HH:mm:ss`
  - `yyyy-MM-dd'T'HH:mm:ss`
  - `yyyy-MM-dd`
  - 时间戳（数字）
  - JSON 对象含 fastTime/time/timestamp 字段
- 统一时区：GMT+8
- Jackson 配置禁止将日期序列化为时间戳：`WRITE_DATES_AS_TIMESTAMPS = false`

### 6.6 依赖注入方式

项目使用 `@Autowired` 字段注入（非构造器注入），这是较旧的做法。现代 Spring Boot 推荐构造器注入，便于测试和不可变性。
